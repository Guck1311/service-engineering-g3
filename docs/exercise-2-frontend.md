## Goal and Scope

The SPA consumes the REST API under `/api/v1` (see the root `README.md`) and offers:

- **Catalogue**: browse and filter all music items (tracks, albums, playlists).
- **Detail page**: metadata, comments and 5-star ratings of one item.
- **My collection**: add or remove items, mark them like/dislike/favourite.
- **All collections**: overview of the collections of all users or of one user.
- **Admin**: create, edit and delete music items.

There is no login (the assignment leaves authentication out). As in the backend, the
caller is identified by the `X-User-Id` header, and the frontend has a **user switcher**
to act as the seeded users `1` = Admin, `2` = Anna or `3` = Ben. This also demonstrates
role-dependent UI.

### Problem: `readonly()` vs. `computed()`

`useAsync` first returned its state with `readonly(data)`. The type check failed:
`readonly()` is **deep**, so `data` became `DeepReadonly<MusicItem>`, which cannot be
passed to code expecting a `MusicItem`. Only the ref itself should be read-only, so the
state is now returned as `computed(() => data.value)`, a computed without a setter.

# Part 2 - Vue.js Reference

## 1. Distinguishing Features

*Introduced in step 1, extended in later steps.*

- **Progressive framework**: Vue can be added to a single page with a `<script>` tag or
  used as a full SPA framework with router, store and build tooling. The core library
  only handles the view layer; routing (`vue-router`) and state (`pinia`) are separate,
  official packages.
- **Single-File Components (SFC)**: a `.vue` file holds a component's template, logic
  (`<script setup>`) and styles (`<style scoped>`) together.
- **HTML-based templates** with directives (`v-if`, `v-for`, `v-model`, `@click`,
  `:prop`), not JSX as in React. The SFC compiler turns templates into optimized render
  functions at build time.
- **Fine-grained reactivity**: `ref()` and `reactive()` values are tracked by JavaScript
  proxies. Vue knows exactly which component depends on which value and re-renders only
  those components. React instead re-runs the whole component function on every state
  change.
- **Virtual DOM with compiler hints**: Vue renders through a virtual DOM, but the
  compiler marks static parts and dynamic bindings, so the diff skips everything static.
- **Composition API** (`<script setup>`, used here) vs. the older **Options API**
  (`data`, `methods`, `computed` objects). Both are supported; the Composition API makes
  it easy to reuse logic in *composables* and works well with TypeScript.
- **Client-side rendering** in our app. Server-side rendering and hydration are
  available through Nuxt, a meta-framework built on Vue, which we don't need.

## 3. State Management

*Introduced in step 6.*

### Three kinds of state

| Kind | Lives in | Example | Shared with |
| --- | --- | --- | --- |
| **Local state** | `ref()` in a component | navbar menu open, form input | only this component (children via props) |
| **URL state** | route params / query | `/catalogue/6`, `?userId=2` | everyone; survives reload, bookmarkable |
| **Global state** | Pinia store | current user, my collection | every component that uses the store |

Local state is the default. State moves to a store only when **several unrelated
components** need it. In our app, the current user is needed by the navbar, the views,
the API layer and the router guard, and the collection by the navbar badge, the
catalogue cards, the detail page and "My collection".

Passing such state down as props through every level ("prop drilling") or sending it up
with events between siblings quickly becomes unmanageable. A store is a single place
that all components read from and write to.

### Reactivity is the foundation

A store is not magic: it is reactive state (`ref`, `computed`) that lives **outside** a
component. Any `ref` defined at module level is already shared state:

```ts
// works, but no devtools, no SSR safety, hard to test
export const currentUserId = ref(2)
```

**Pinia** (the official store library, successor of Vuex) adds structure on top: a
store per domain, devtools integration (inspect and time-travel state), HMR, plugins,
and test isolation (a fresh Pinia per test).

### Defining a store (setup syntax)

Setup stores use the same Composition API as components: `ref` = state,
`computed` = getters, functions = actions.

```ts
// stores/session.ts
export const useSessionStore = defineStore('session', () => {
  // state
  const users = ref<User[]>([])
  const currentUserId = ref(readStoredUserId() ?? DEFAULT_USER_ID)

  // getters
  const currentUser = computed(() => users.value.find((u) => u.id === currentUserId.value) ?? null)
  const isAdmin = computed(() => currentUser.value?.role === 'ADMIN')

  // side effects: connect the API layer, persist the choice
  setUserIdProvider(() => currentUserId.value)
  watch(currentUserId, storeUserId)

  // actions
  async function loadUsers() { users.value = await usersService.list() }
  function switchUser(id: number) { currentUserId.value = id }

  return { users, currentUserId, currentUser, isAdmin, loadUsers, switchUser }
})
```

Pinia also supports an **options syntax** (`state`, `getters`, `actions` objects),
similar to Vuex and the Options API. We use setup stores for consistency with
`<script setup>`.

The store is created lazily on the first `useSessionStore()` call and then exists
**once for the whole app**. Every component calling it gets the same instance. (A
composable like `useAsync`, by contrast, creates new state on every call.)

### Using a store in components

```vue
<script setup lang="ts">
const session = useSessionStore()
// destructuring would lose reactivity -> storeToRefs keeps state and getters as refs
const { users, currentUserId, isAdmin } = storeToRefs(session)
</script>

<template>
  <select :value="currentUserId" @change="session.switchUser(Number(($event.target as HTMLSelectElement).value))">
    <option v-for="user in users" :key="user.id" :value="user.id">{{ user.name }}</option>
  </select>
  <RouterLink v-if="session.isAdmin" :to="{ name: 'item-create' }">New item</RouterLink>
</template>
```

When `currentUserId` changes, **every** component that read it re-renders: the
switcher, the admin buttons in the views, the navbar badge (through the collection
store, which reloads).

### Stores using stores, and watchers inside stores

```ts
// stores/collection.ts
export const useCollectionStore = defineStore('collection', () => {
  const session = useSessionStore()          // a store may use other stores
  const entries = ref<CollectionEntry[]>([])
  const count = computed(() => entries.value.length)

  watch(() => session.currentUserId, () => {  // another user: reload the collection
    entries.value = []
    void load()
  })
  // ...
})
```

### Stores outside of components

Stores can be used anywhere after `app.use(createPinia())`, e.g. in the router guard.
The call must happen **inside** the guard, not at module level, where Pinia is not
installed yet:

```ts
router.beforeEach(async (to) => {
  if (!to.meta.requiresAdmin) return true
  const session = useSessionStore()
  await session.ensureLoaded()   // on a direct page load the users may not be loaded yet
  return session.isAdmin ? true : { name: 'catalogue', query: { denied: to.fullPath } }
})
```

The API layer does **not** import the store. Instead, the store registers a provider
function (`setUserIdProvider`), so the dependency points from the UI state to the API
layer and the API layer stays independent of Vue.

### Optimistic updates

When the user clicks "like", waiting for the server makes the UI feel slow. The
collection store shows the change **immediately** and corrects it if the server
disagrees:

```ts
async function update(musicItemId: number, changes: UpdateCollectionEntry) {
  const previous = entryFor(musicItemId)!
  replaceEntry({ ...previous, ...changes })          // 1. show at once
  try {
    replaceEntry(await collectionsService.update(session.currentUserId, musicItemId, changes)) // 2. take the server's version
  } catch (e) {
    replaceEntry(previous)                           // 3. roll back
    throw ApiError.from(e)                           //    and let the UI show the error
  }
}
```

The store also enforces the backend rule "a disliked item cannot be a favourite" before
sending (disliking removes the favourite flag), so the user never runs into the 400.

### Immutable updates

The store replaces arrays and objects instead of mutating them
(`entries.value = entries.value.map(...)`). Vue would also detect in-place mutations of
a `ref` array, but replacing makes the change explicit, keeps the previous object intact
for the rollback, and works with `shallowRef` too.

## 4. Styling of UI Elements

*Introduced in step 2.*

Vue itself has no styling system. It offers several ways to attach CSS to components,
and any CSS framework can be added. We combine **Bootstrap** (layout, components,
utility classes) with **SCSS** (theme) and Vue's **scoped styles** (component-specific
styles).

### Three levels of styles

| Level | Where | Applies to | Our use |
| --- | --- | --- | --- |
| Global | `src/styles/main.scss`, imported in `main.ts` | whole app | Bootstrap + theme, `.card-hover` |
| Scoped | `<style scoped>` in a `.vue` file | only this component | gradient brand text in `AppNavbar` |
| Inline / bound | `class` / `:class` / `:style` in the template | one element | Bootstrap utility classes, `show` toggle |

Vue also supports **CSS Modules** (`<style module>`, accessed as `$style.x`) and
`v-bind()` inside `<style>` to use reactive values in CSS. We don't need either.

### Theming Bootstrap with SCSS

Every Bootstrap variable is declared with `!default` ("only if not set yet"). Setting
the variable **before** importing Bootstrap changes every component that uses it:

```scss
// styles/_variables.scss
$primary: #6f42c1;        // buttons, links, badges, navbar bg-primary, ...
$border-radius: 0.5rem;
$card-border-width: 0;

// styles/main.scss
@import 'variables';                 // 1. our values
@import 'bootstrap/scss/bootstrap';  // 2. Bootstrap compiled with them
.card-hover:hover { box-shadow: $box-shadow; }  // 3. own styles using Bootstrap variables
```

This is the advantage over loading the precompiled `bootstrap.css`: the theme is applied
at build time, consistently, without overriding CSS rules afterwards.

### Scoped styles

```vue
<!-- AppNavbar.vue -->
<span class="brand-text">Music Collection</span>

<style scoped lang="scss">
@use '@/styles/variables' as *;   // shared SCSS variables inside a component
.brand-text { background: $navbar-brand-gradient; background-clip: text; color: transparent; }
</style>
```

The SFC compiler adds a unique attribute (e.g. `data-v-7a3f1c`) to every element of the
component and rewrites the selector to `.brand-text[data-v-7a3f1c]`. The style cannot
leak into other components, and other components' `.brand-text` classes don't affect
this one. `lang="scss"` lets each component use SCSS too.

### Class bindings instead of DOM manipulation

Bootstrap's own JavaScript opens the mobile menu by adding the class `show` to the
element directly. In Vue, the template should be the only thing that changes the DOM,
so the class is **bound to reactive state** instead:

```vue
<script setup lang="ts">
const menuOpen = ref(false)
</script>

<button class="navbar-toggler" :aria-expanded="menuOpen" @click="menuOpen = !menuOpen">…</button>
<div class="collapse navbar-collapse" :class="{ show: menuOpen }">…</div>
```

`:class` accepts a string, an array (`['bi', `bi-${item.icon}`]`) or an object
(`{ show: menuOpen }`: the class is set while the value is truthy). When `menuOpen`
changes, Vue updates exactly this attribute. Therefore we don't load Bootstrap's
JavaScript bundle at all.

### Icons

`bootstrap-icons` is an icon *font*: `import 'bootstrap-icons/font/bootstrap-icons.css'`
once in `main.ts`, then `<i class="bi bi-heart"></i>` anywhere. Vite copies the font
files into the build and adds a content hash to their file names for caching.

## 5. Routing and Navigation

*Introduced in step 3.*

In an SPA the browser loads `index.html` only once. When the user clicks a link, the
**client-side router** intercepts the click, changes the URL via the History API
(`history.pushState`) and swaps the component shown in `<RouterView>`. Nothing is
requested from the server. Vue's official router is **Vue Router**.

### Setup

```ts
// router/index.ts
const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    { path: '/catalogue', name: 'catalogue', component: CatalogueView },
    { path: '/catalogue/:id(\\d+)', name: 'item-detail',
      component: () => import('@/views/MusicItemDetailView.vue'),
      props: (route) => ({ id: Number(route.params.id) }) },
    // ...
    { path: '/:pathMatch(.*)*', name: 'not-found', component: () => import('@/views/NotFoundView.vue') },
  ],
})

// main.ts
app.use(router)
```

```vue
<!-- App.vue: the matched component is rendered here -->
<AppNavbar />
<main><RouterView /></main>
```

### Concepts

| Concept | Example | Purpose |
| --- | --- | --- |
| **History mode** | `createWebHistory()` | real URLs (`/catalogue/6`). Alternative: `createWebHashHistory()` → `/#/catalogue/6` |
| **Named routes** | `{ name: 'item-detail', params: { id: 6 } }` | links don't hard-code paths |
| **Dynamic segments** | `:id(\\d+)` | parameter with a regex: `/catalogue/abc` doesn't match |
| **Route props** | `props: (route) => ({ id: Number(route.params.id) })` | the view gets a typed prop and doesn't depend on the router |
| **Query parameters** | `/collections?userId=2` | optional state that belongs in the URL (filters) |
| **Redirect** | `{ path: '/', redirect: { name: 'catalogue' } }` | |
| **Catch-all (404)** | `/:pathMatch(.*)*` | must match last |
| **Lazy loading** | `component: () => import('...')` | separate chunk, loaded on the first visit |
| **Route meta** | `meta: { title, requiresAdmin }` | custom data per route, read by guards |
| **Guards** | `router.beforeEach`, `router.afterEach` | run around every navigation (title now, admin check in step 6) |
| **Scroll behaviour** | `scrollBehavior` | restore the scroll position on Back, otherwise start at the top |

### Navigating

**Declarative:** `<RouterLink>` renders an `<a href>`. A normal click is handled by the
router, while Ctrl+click or "open in new tab" still work because it is a real link.

```vue
<RouterLink :to="{ name: 'item-detail', params: { id: item.id } }">{{ item.title }}</RouterLink>
```

**Programmatic:** `useRouter()` returns the router instance, for navigation after an
action:

```ts
const router = useRouter()
router.push({ name: 'item-detail', params: { id } })    // new history entry
router.replace({ name: 'item-detail', params: { id } }) // replaces the current entry (after saving a form)
router.replace({ query: { userId: '2' } })              // only change the query (filter)
router.back()                                           // browser Back
```

**Reading the current route:** `useRoute()` returns a *reactive* route object.
Templates and `computed` values that use it update automatically after each navigation:

```ts
const route = useRoute()
const isActive = (to: string) => route.path === to || route.path.startsWith(`${to}/`)
```

### Route props instead of `useRoute()` in views

A view *could* read `useRoute().params.id` itself, but then it only works under exactly
that URL, and the parameter is always a string. With `props`, the router converts it,
and the view just declares what it needs:

```ts
// MusicItemDetailView.vue
const props = defineProps<{ id: number }>()
```

`MusicItemEditView` uses this for two routes: `/catalogue/new` passes no `id` (create),
`/catalogue/:id/edit` passes one (edit).

### State in the URL

The user filter of the overview page is kept in the **query string**, not only in a
component variable. A filtered page can therefore be bookmarked, reloaded and shared, and
Back/Forward restore earlier filters. When the query changes, the router passes a new
`userId` prop and the view updates.

### Typed route meta

```ts
declare module 'vue-router' {
  interface RouteMeta { title?: string; requiresAdmin?: boolean }
}

router.afterEach((to) => {
  document.title = to.meta.title ? `${to.meta.title} · Music Collection Manager` : 'Music Collection Manager'
})
```

Declaration merging extends Vue Router's `RouteMeta` type, so `to.meta.requiresAdmin` is
type-checked. The admin guard (`beforeEach`) that uses this flag follows with the user
state in step 6.

### Active links

`<RouterLink>` adds `router-link-active` / `router-link-exact-active` automatically.
These are based on **nested route records**, not path prefixes: with our flat routes,
the "Catalogue" link would not be active on `/catalogue/6`. The navbar therefore binds
Bootstrap's `active` class itself, comparing `useRoute().path` with each entry's prefix.

### Deployment note

History mode needs the web server to answer every unknown path with `index.html`
(otherwise reloading `/catalogue/6` gives the server's 404). Vite's dev server does
this automatically. For static hosting such as GitHub Pages, this is handled in step 9.

## 6. Separating Logic from UI Components

*Introduced in step 5, stores in step 6.*

Components should mostly **display** data and **forward** user actions. Everything else
goes into separate modules. Unlike Angular, Vue has no dependency-injection-based service
concept. It uses plain ES modules, and for reactive logic, **composables**.

| Kind | Example | Contains | Uses Vue? | State |
| --- | --- | --- | --- | --- |
| **Service** | `musicItemsService.get(id)` | endpoint calls, request/response types | no | none |
| **Utility** | `formatDuration(259)` | pure functions | no | none |
| **Composable** | `useAsync(fn)` | reusable reactive logic | yes (`ref`, `computed`, lifecycle hooks) | **one copy per component** that calls it |
| **Store** (step 6) | `useSessionStore()` | state shared by the app | yes (Pinia) | **one copy for the whole app** |
| **Component** | `CatalogueView.vue` | template, wiring | yes | UI state only (e.g. "menu open") |

### Services

A service is a plain object with one async function per endpoint. It knows URLs, HTTP
methods and types, and returns the response body:

```ts
// services/music-items.service.ts
export const musicItemsService = {
  async list(query: MusicItemQuery = {}): Promise<Page<MusicItem>> {
    const { data } = await http.get<Page<MusicItem>>('/music-items', { params: query })
    return data
  },
  async get(id: number): Promise<MusicItem> { … },
  async create(item: CreateMusicItem): Promise<MusicItem> { … },
  async update(id: number, item: UpdateMusicItem): Promise<MusicItem> { … },
  async remove(id: number): Promise<void> { … },
}
```

Why:

- **One place per endpoint.** If a URL changes, only the service changes.
- **Components stay small.** `await musicItemsService.get(id)` instead of URL building,
  headers and response unpacking.
- **Testable without a browser.** Services are plain functions (see the service tests).
- **Reusable.** The same function serves the detail page, the edit form and a store.

### Composables

A composable is a function named `useXxx()` that uses Vue's reactivity API and returns
reactive state. It is Vue's main tool for reusing **stateful** logic between components,
comparable to React hooks (but it runs only once per component, during `setup`).

`useAsync` wraps any async function and provides `loading`, `error` and `data`:

```ts
// composables/useAsync.ts (simplified)
export function useAsync<T, A extends unknown[]>(fn: (...args: A) => Promise<T>) {
  const data = shallowRef<T>()
  const error = shallowRef<ApiError | null>(null)
  const loading = ref(false)
  let latestCall = 0

  async function run(...args: A) {
    const call = ++latestCall
    loading.value = true
    error.value = null
    try {
      const result = await fn(...args)
      if (call === latestCall) data.value = result // ignore outdated responses
      return result
    } catch (e) {
      if (call === latestCall) error.value = ApiError.from(e)
    } finally {
      if (call === latestCall) loading.value = false
    }
  }

  return { data: computed(() => data.value), error: computed(() => error.value),
           loading: computed(() => loading.value), run }
}
```

```vue
<!-- usage in a component -->
<script setup lang="ts">
const props = defineProps<{ id: number }>()
const { data: item, loading, error, run } = useAsync(musicItemsService.get)
onMounted(() => run(props.id))
</script>

<template>
  <div v-if="loading" class="spinner-border" />
  <div v-else-if="error" class="alert alert-danger">{{ error.message }}</div>
  <h1 v-else-if="item">{{ item.title }}</h1>
</template>
```

Details:

- **Each call creates new state.** Two components calling `useAsync` don't share
  anything. Shared state is what stores are for.
- **`shallowRef`**: API results are replaced as a whole, never mutated deeply, so Vue
  only tracks the reference, not every nested property.
- **Race condition protection**: when calls overlap (typing "ab", then "abbey" in a
  search field), the response for "ab" may arrive *after* the one for "abbey".
  `latestCall` makes sure only the newest call updates the state.
- **Read-only state**: the component can read `loading`, `error`, `data` but only change
  them through `run()`. `computed()` instead of `readonly()` keeps the types plain (see
  step 5).
- **Never throws**: errors become state the template can show. Section 8 covers how
  errors reach the user.

### Utilities

Pure functions without Vue, e.g. `formatDuration(259) → "4:19"`,
`formatDate(iso) → "19 Nov 2026"` (with `Intl.DateTimeFormat`). Templates call them
directly: `{{ formatDuration(item.durationSeconds) }}`.

## 7. Communication with the Backend

*Introduced in step 4.*

Vue has no built-in HTTP client (unlike Angular's `HttpClient`). Any library works: the
browser's `fetch`, axios, ky, ... We use **axios** with one central instance, and
**types generated from the backend's OpenAPI spec**.

### Layers

```
View / component          calls a store or service, shows data and errors
      │
Pinia store (step 6)      shared state, e.g. the current user's collection
      │
Service (step 5)          one function per endpoint: getMusicItem(id), addToCollection(...)
      │
http.ts                   axios instance: base URL, X-User-Id header, ApiError conversion
      │
REST API /api/v1          NestJS backend (Exercise 1)
```

Components never build URLs or call axios themselves. This keeps them small and
testable (see section 6).

### Type-safe DTOs from OpenAPI

The backend documents every DTO with `@nestjs/swagger` and serves the OpenAPI spec at
`/api/docs-json`. `openapi-typescript` converts it into TypeScript types:

```ts
// schema.d.ts (generated)
MusicItemDto: {
  id: number
  type: components['schemas']['MusicItemType']   // 'TRACK' | 'ALBUM' | 'PLAYLIST'
  title: string
  artist: string | null
  trackCount: number | null
  averageRating: number | null
  createdAt: string                              // JSON has no Date type
  // ...
}

// types.ts (handwritten aliases)
export type MusicItem = components['schemas']['MusicItemDto']
export type MusicItemQuery = NonNullable<paths['/api/v1/music-items']['get']['parameters']['query']>
```

The backend is the **single source of truth**. If it renames or removes a field, the
next `npm run api:types` turns every outdated use in the frontend into a compile error.
Without this, the mismatch shows up only at runtime, as `undefined` in the UI. Our first
frontend attempt had exactly this problem when `trackIds` was replaced by `trackCount`.

### The axios instance

```ts
// api/http.ts
export const http = axios.create({
  baseURL: import.meta.env.VITE_API_URL, // from .env, different per environment
  timeout: 60_000,                       // Render's free plan needs ~30-50 s to wake up
})
```

`import.meta.env` contains the variables from `.env` files that start with `VITE_`.
Vite replaces them at **build time**, so they end up in the JavaScript bundle and must
never contain secrets. For deployment the URL is set when building:
`VITE_API_URL=https://…/api/v1 npm run build`.

The backend enables CORS, so the browser may call `localhost:3000` from the dev server
on `localhost:5173`. Alternatively, Vite's `server.proxy` could forward `/api` to the
backend; we don't need that.

### Interceptors

Interceptors are functions that axios runs for **every** request or response. They hold
the cross-cutting logic that would otherwise be repeated in every call:

```ts
// before every request: identify the caller
http.interceptors.request.use((config) => {
  const userId = currentUserId()
  if (userId !== null) config.headers.set('X-User-Id', String(userId))
  return config
})

// after every response: success passes through, every failure becomes an ApiError
http.interceptors.response.use(
  (response) => response,
  (error) => Promise.reject(ApiError.from(error)),
)
```

The current user lives in a Pinia store (step 6), but the API layer should not depend on
UI state. So `http.ts` only offers `setUserIdProvider(fn)`, and the store registers a
function that returns the selected id. The dependency points from the store to the API
layer, not the other way round.

### One error type: `ApiError`

The backend's exception filter sends every error in one format:

```json
{ "statusCode": 404, "error": "Not Found", "message": "Music item 999 not found",
  "path": "/api/v1/music-items/999", "timestamp": "2026-11-19T17:43:00.231Z" }
```

`message` is a list for validation errors. `ApiError.from()` turns every failure into
one class with a readable message:

| Situation | `kind` | `status` | `message` | `details` |
| --- | --- | --- | --- | --- |
| backend error (4xx/5xx) | `http` | 404, 403, … | backend's message | - |
| validation error | `http` | 400 | "Please check your input." | individual messages |
| backend down / offline / CORS | `network` | 0 | "The server cannot be reached. Is the backend running?" | - |
| no answer within 60 s | `timeout` | 0 | "The server took too long to respond. Please try again." | - |
| aborted on purpose | `canceled` | 0 | - | - |

How the UI displays these errors follows in section 8.

### Testing without a backend

Axios sends requests through an exchangeable **adapter**. The tests replace it with a
function that returns a prepared response, so the interceptors can be tested without
network access:

```ts
http.defaults.adapter = async (config) => {
  const response = { status: 404, data: { message: 'Music item 999 not found' }, config, headers: {}, statusText: '' }
  throw new AxiosError('error', AxiosError.ERR_BAD_REQUEST, config, {}, response)
}
const error = await http.get('/music-items/999').catch((e) => e)
expect(error).toMatchObject({ kind: 'http', status: 404, message: 'Music item 999 not found' })
```
