## Goal and Scope

The SPA consumes the REST API under `/api/v1` (see the root `README.md`) and offers:

- **Catalogue**: browse and filter all music items (tracks, albums, playlists).
- **Detail page**: metadata, comments and 5-star ratings of one item.
- **My collection**: add or remove items, mark them like/dislike/favourite.
- **All collections**: overview of the collections of all users or of one user.
- **Admin**: create, edit and delete music items.

There is no login (the assignment leaves authentication out). As in the backend, the
caller is identified by the `X-User-Id` header, and the frontend has a **user switcher**
to act as the seeded users `1` = Admin, `2` = Anna or `3` = Ben. This also demonstrates
role-dependent UI.

### How the app starts

`index.html` is the only HTML page the server ever delivers. Everything else is rendered
by JavaScript in the browser, which is what makes it a *Single Page Application*:

```ts
// src/main.ts
const app = createApp(App) // 1. create the app with the root component
app.use(createPinia())     // 2. install plugins: state management ...
app.use(router)            //    ... and routing
app.mount('#app')          // 3. render App.vue into <div id="app"> of index.html
```

### Sass deprecation warnings

Bootstrap 5.3 is written with Sass `@import`, which current Dart Sass deprecates in
favour of the module system (`@use`). Since Bootstrap can only be themed via `@import`
until Bootstrap 6, the build printed 21 warnings. They are silenced in
`vite.config.ts`:

```ts
css: {
  preprocessorOptions: {
    scss: {
      quietDeps: true,                 // warnings from inside node_modules
      silenceDeprecations: ['import'], // our own @import of Bootstrap
    },
  },
},
```

### Result

- `npm run build`: no warnings. The CSS bundle (all of Bootstrap) is 307 kB, 45 kB
  gzipped. Importing only the Bootstrap partials we use would make it smaller; not worth
  it for this project.
- `npm run test:unit`: 2 tests for the navbar (rendering, mobile toggle).

# Part 2 - Vue.js Reference

## 1. Distinguishing Features

*Introduced in step 1, extended in later steps.*

- **Progressive framework**: Vue can be added to a single page with a `<script>` tag or
  used as a full SPA framework with router, store and build tooling. The core library
  only handles the view layer; routing (`vue-router`) and state (`pinia`) are separate,
  official packages.
- **Single-File Components (SFC)**: a `.vue` file holds a component's template, logic
  (`<script setup>`) and styles (`<style scoped>`) together.
- **HTML-based templates** with directives (`v-if`, `v-for`, `v-model`, `@click`,
  `:prop`), not JSX as in React. The SFC compiler turns templates into optimized render
  functions at build time.
- **Fine-grained reactivity**: `ref()` and `reactive()` values are tracked by JavaScript
  proxies. Vue knows exactly which component depends on which value and re-renders only
  those components. React instead re-runs the whole component function on every state
  change.
- **Virtual DOM with compiler hints**: Vue renders through a virtual DOM, but the
  compiler marks static parts and dynamic bindings, so the diff skips everything static.
- **Composition API** (`<script setup>`, used here) vs. the older **Options API**
  (`data`, `methods`, `computed` objects). Both are supported; the Composition API makes
  it easy to reuse logic in *composables* and works well with TypeScript.
- **Client-side rendering** in our app. Server-side rendering and hydration are
  available through Nuxt, a meta-framework built on Vue, which we don't need.

## 4. Styling of UI Elements

*Introduced in step 2.*

Vue itself has no styling system. It offers several ways to attach CSS to components,
and any CSS framework can be added. We combine **Bootstrap** (layout, components,
utility classes) with **SCSS** (theme) and Vue's **scoped styles** (component-specific
styles).

### Three levels of styles

| Level | Where | Applies to | Our use |
| --- | --- | --- | --- |
| Global | `src/styles/main.scss`, imported in `main.ts` | whole app | Bootstrap + theme, `.card-hover` |
| Scoped | `<style scoped>` in a `.vue` file | only this component | gradient brand text in `AppNavbar` |
| Inline / bound | `class` / `:class` / `:style` in the template | one element | Bootstrap utility classes, `show` toggle |

Vue also supports **CSS Modules** (`<style module>`, accessed as `$style.x`) and
`v-bind()` inside `<style>` to use reactive values in CSS. We don't need either.

### Theming Bootstrap with SCSS

Every Bootstrap variable is declared with `!default` ("only if not set yet"). Setting
the variable **before** importing Bootstrap changes every component that uses it:

```scss
// styles/_variables.scss
$primary: #6f42c1;        // buttons, links, badges, navbar bg-primary, ...
$border-radius: 0.5rem;
$card-border-width: 0;

// styles/main.scss
@import 'variables';                 // 1. our values
@import 'bootstrap/scss/bootstrap';  // 2. Bootstrap compiled with them
.card-hover:hover { box-shadow: $box-shadow; }  // 3. own styles using Bootstrap variables
```

This is the advantage over loading the precompiled `bootstrap.css`: the theme is applied
at build time, consistently, without overriding CSS rules afterwards.

### Scoped styles

```vue
<!-- AppNavbar.vue -->
<span class="brand-text">Music Collection</span>

<style scoped lang="scss">
@use '@/styles/variables' as *;   // shared SCSS variables inside a component
.brand-text { background: $navbar-brand-gradient; background-clip: text; color: transparent; }
</style>
```

The SFC compiler adds a unique attribute (e.g. `data-v-7a3f1c`) to every element of the
component and rewrites the selector to `.brand-text[data-v-7a3f1c]`. The style cannot
leak into other components, and other components' `.brand-text` classes don't affect
this one. `lang="scss"` lets each component use SCSS too.

### Class bindings instead of DOM manipulation

Bootstrap's own JavaScript opens the mobile menu by adding the class `show` to the
element directly. In Vue, the template should be the only thing that changes the DOM,
so the class is **bound to reactive state** instead:

```vue
<script setup lang="ts">
const menuOpen = ref(false)
</script>

<button class="navbar-toggler" :aria-expanded="menuOpen" @click="menuOpen = !menuOpen">…</button>
<div class="collapse navbar-collapse" :class="{ show: menuOpen }">…</div>
```

`:class` accepts a string, an array (`['bi', `bi-${item.icon}`]`) or an object
(`{ show: menuOpen }`: the class is set while the value is truthy). When `menuOpen`
changes, Vue updates exactly this attribute. Therefore we don't load Bootstrap's
JavaScript bundle at all.

### Icons

`bootstrap-icons` is an icon *font*: `import 'bootstrap-icons/font/bootstrap-icons.css'`
once in `main.ts`, then `<i class="bi bi-heart"></i>` anywhere. Vite copies the font
files into the build and adds a content hash to their file names for caching.

## 5. Routing and Navigation

*Introduced in step 3.*

In an SPA the browser loads `index.html` only once. When the user clicks a link, the
**client-side router** intercepts the click, changes the URL via the History API
(`history.pushState`) and swaps the component shown in `<RouterView>`. Nothing is
requested from the server. Vue's official router is **Vue Router**.

### Setup

```ts
// router/index.ts
const router = createRouter({
  history: createWebHistory(import.meta.env.BASE_URL),
  routes: [
    { path: '/catalogue', name: 'catalogue', component: CatalogueView },
    { path: '/catalogue/:id(\\d+)', name: 'item-detail',
      component: () => import('@/views/MusicItemDetailView.vue'),
      props: (route) => ({ id: Number(route.params.id) }) },
    // ...
    { path: '/:pathMatch(.*)*', name: 'not-found', component: () => import('@/views/NotFoundView.vue') },
  ],
})

// main.ts
app.use(router)
```

```vue
<!-- App.vue: the matched component is rendered here -->
<AppNavbar />
<main><RouterView /></main>
```

### Concepts

| Concept | Example | Purpose |
| --- | --- | --- |
| **History mode** | `createWebHistory()` | real URLs (`/catalogue/6`). Alternative: `createWebHashHistory()` → `/#/catalogue/6` |
| **Named routes** | `{ name: 'item-detail', params: { id: 6 } }` | links don't hard-code paths |
| **Dynamic segments** | `:id(\\d+)` | parameter with a regex: `/catalogue/abc` doesn't match |
| **Route props** | `props: (route) => ({ id: Number(route.params.id) })` | the view gets a typed prop and doesn't depend on the router |
| **Query parameters** | `/collections?userId=2` | optional state that belongs in the URL (filters) |
| **Redirect** | `{ path: '/', redirect: { name: 'catalogue' } }` | |
| **Catch-all (404)** | `/:pathMatch(.*)*` | must match last |
| **Lazy loading** | `component: () => import('...')` | separate chunk, loaded on the first visit |
| **Route meta** | `meta: { title, requiresAdmin }` | custom data per route, read by guards |
| **Guards** | `router.beforeEach`, `router.afterEach` | run around every navigation (title now, admin check in step 6) |
| **Scroll behaviour** | `scrollBehavior` | restore the scroll position on Back, otherwise start at the top |

### Navigating

**Declarative:** `<RouterLink>` renders an `<a href>`. A normal click is handled by the
router, while Ctrl+click or "open in new tab" still work because it is a real link.

```vue
<RouterLink :to="{ name: 'item-detail', params: { id: item.id } }">{{ item.title }}</RouterLink>
```

**Programmatic:** `useRouter()` returns the router instance, for navigation after an
action:

```ts
const router = useRouter()
router.push({ name: 'item-detail', params: { id } })    // new history entry
router.replace({ name: 'item-detail', params: { id } }) // replaces the current entry (after saving a form)
router.replace({ query: { userId: '2' } })              // only change the query (filter)
router.back()                                           // browser Back
```

**Reading the current route:** `useRoute()` returns a *reactive* route object.
Templates and `computed` values that use it update automatically after each navigation:

```ts
const route = useRoute()
const isActive = (to: string) => route.path === to || route.path.startsWith(`${to}/`)
```

### Route props instead of `useRoute()` in views

A view *could* read `useRoute().params.id` itself, but then it only works under exactly
that URL, and the parameter is always a string. With `props`, the router converts it,
and the view just declares what it needs:

```ts
// MusicItemDetailView.vue
const props = defineProps<{ id: number }>()
```

`MusicItemEditView` uses this for two routes: `/catalogue/new` passes no `id` (create),
`/catalogue/:id/edit` passes one (edit).

### State in the URL

The user filter of the overview page is kept in the **query string**, not only in a
component variable. A filtered page can therefore be bookmarked, reloaded and shared, and
Back/Forward restore earlier filters. When the query changes, the router passes a new
`userId` prop and the view updates.

### Typed route meta

```ts
declare module 'vue-router' {
  interface RouteMeta { title?: string; requiresAdmin?: boolean }
}

router.afterEach((to) => {
  document.title = to.meta.title ? `${to.meta.title} · Music Collection Manager` : 'Music Collection Manager'
})
```

Declaration merging extends Vue Router's `RouteMeta` type, so `to.meta.requiresAdmin` is
type-checked. The admin guard (`beforeEach`) that uses this flag follows with the user
state in step 6.

### Active links

`<RouterLink>` adds `router-link-active` / `router-link-exact-active` automatically.
These are based on **nested route records**, not path prefixes: with our flat routes,
the "Catalogue" link would not be active on `/catalogue/6`. The navbar therefore binds
Bootstrap's `active` class itself, comparing `useRoute().path` with each entry's prefix.

### Deployment note

History mode needs the web server to answer every unknown path with `index.html`
(otherwise reloading `/catalogue/6` gives the server's 404). Vite's dev server does
this automatically. For static hosting such as GitHub Pages, this is handled in step 9.
